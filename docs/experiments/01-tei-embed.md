# Эксперимент 1. Шаг 2: перевод текста в числа через TEI

## Цель

Проверить, что TEI с моделью bge-m3 работает на ноутбуке и что числа действительно отражают смысл: тексты на одну тему ближе друг к другу, чем тексты на разные темы.

## Как запускали

1. `docker compose up -d tei` — TEI в контейнере (`infra/tei`), порт 8081.
2. `uv run python evals/check_embed.py`.

Скрипт переводит в числа три текста — два про возврат денег и один про доставку — и сравнивает их близость.

## Результаты

См. [01-tei-embed-results.md](01-tei-embed-results.md) — файл создаётся скриптом.

## Выводы

**Попробовали:** запустить TEI с моделью bge-m3 в Docker на MacBook M4 (через эмуляцию x86) и перевести в числа три текста: два про возврат денег и один про доставку.

**Поняли:**
- TEI работает на ноутбуке в Docker. На каждый текст приходит 1024 числа, как и ожидалось.
- Скорость: 250 мс на один текст, 1023 мс на три текста одним запросом. Отправка пачкой на ноутбуке быстрее не стала (около 340 мс на текст против 250 мс по одному) — вероятно, из-за эмуляции и работы только на процессоре.
- Числа отражают смысл: тексты про возврат денег близки на 0.806, а текст про возврат и текст про доставку — на 0.669. Проверка пройдена.
- Близость разных по смыслу текстов тоже высокая (0.669), потому что все три про заказы. Значит, нельзя решать «подходит / не подходит» по одному порогу близости. Числа годятся, чтобы отобрать похожие кусочки и выстроить их по порядку, а точный отбор нужен отдельно — это шаг 4 (реранкер).
- Для worker 250 мс на вопрос клиента — приемлемо. Для kb-index: 1000 кусочков статей займут около 4 минут на ноутбуке. Это допустимо, потому что индексация идёт заранее, а не во время вопроса клиента.

**Решили:**
- TEI с bge-m3 в Docker подходит для шага 2 и для kb-index — оставляем.
- Следующий шаг — подключить модель Qwen для шага 1 (определение темы вопроса).
- Порог близости в коде не задаём: на шаге 3 берём 20 самых близких кусочков, а точность обеспечит реранкер на шаге 4.
