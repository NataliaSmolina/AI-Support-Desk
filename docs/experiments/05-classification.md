# Неделя 5: правила классификации и парное сравнение промптов

## Изменение поведения

Классификатор по-прежнему возвращает `category`, `priority`, `sentiment`,
`wants_human`. Схема и транспорт не менялись. Обновлены правила в системном
промпте, а не добавлена подмена результата модели ключевыми словами.

- Приоритет определяется по фактам: ошибочное списание, посторонний доступ
  или явная срочность текущей проблемы → `critical`; конкретная проблема
  или просьба об операторе → `normal`; общий вопрос → `low`.
- Капслок, раздражение и срок задержки сами по себе не повышают приоритет.
- `wants_human` учитывает актуальную просьбу о человеке, отрицания, прошлые
  разговоры и явно выраженную смену решения. Критическая проблема не означает
  автоматически `wants_human=true`.
- При нескольких темах выбирается критическая проблема, иначе основная просьба,
  при равнозначности — первая. Просьба об операторе не стирает предметную тему.

Это правила проекта, а не универсальный стандарт поддержки. Неоднозначные
эталоны следует согласовывать до сравнения, не менять ради улучшения цифр.

## Данные

- `evals/data/classify_questions.json`: исходные 10 случаев, без изменений.
- `evals/data/classify_validation.json`: 20 дополнительных случаев. Они не
  повторяют вопросы baseline и примеры промпта, но составлены при разработке
  правил. Это регрессионный проверочный набор, а не независимая оценка на
  реальном потоке. Для оценки обобщения нужны отдельно размеченные обращения.
- `evals/prompts/classifier_v1.txt`: точный текст прежнего промпта.

## Самостоятельная проверка

Запустить Docker/Ollama, дождаться установки модели, затем из корня:

```bash
uv run pytest libs/ai-clients/tests evals/tests -q
uv run python -m ai_clients.readiness
uv run python -m evals.compare_classification --limit 1 --output /tmp/week05-smoke.json
```

Smoke выполняет два прогрева и четыре измеряемых запроса: по одному вопросу
из каждого набора для каждого промпта. Он проверяет запуск, но не качество
на полном наборе. На CPU даже этот прогон может быть долгим.

Полное сравнение — два прогрева плюс 60 измеряемых запросов:

```bash
uv run python -m evals.compare_classification --output /tmp/week05-classification.json
```

Один сервер, модель, параметры генерации и таймаут для обоих промптов.
Порядок `before`/`after` чередуется между вопросами, прогрев не входит в среднее.
Запросы выполняются последовательно. Не запускайте параллельно baseline и другие
нагрузочные проверки. Смена промпта меняет кэш контекста, поэтому задержки здесь
описывают именно парный прогон, а не максимальную производительность сервера.

Отчёт сохраняет тексты промптов, SHA-256 наборов, конфигурацию, версию сервера,
каждый ответ, расхождения, технические ошибки и время. Сводки отдельно для
baseline и validation включают точное совпадение, число правильных ответов
по полям, число ошибок и среднее время успешного запроса.

Отчёт обновляется после каждого измерения. Завершённый прогон содержит
`complete: true`; ограниченный запуск — `partial: true`. Отсутствие
`complete: true` означает, что прогон не завершён. Код выхода 0 означает
полное совпадение нового промпта на выбранных случаях и успешные прогревы;
1 — есть несовпадения/ошибки. Это строгий критерий, а не гарантия улучшения.
Старый промпт может иметь ошибки даже при коде выхода 0.

Сравните `datasets.baseline.summary.before` и `.after`, затем такие же сводки
в `datasets.validation`. Улучшение priority/wants_human не должно скрывать
регрессии category/sentiment. Автотесты проверяют контракт и расчёт метрик,
но не доказывают качество реальной модели. Исторические отчёты не перезаписываются.
