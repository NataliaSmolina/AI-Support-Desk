# RAG: вопрос → TEI → PostgreSQL → ответ Ollama

Компонент реализован в общей библиотеке `ai-clients`. Он использует существующие
таблицы `kb_documents` и `kb_chunks`, существующий клиент TEI и генератор ответов.
Код очереди Worker и Telegram-бота не менялся. Классификация и обработка
`wants_human` остаются перед вызовом этого компонента в Worker.

## Самостоятельная проверка на настоящих сервисах

Нужны Docker Desktop, зависимости проекта и существующие настройки TEI/Ollama.
Запускайте команды из корня проекта.

```bash
uv sync --locked
docker compose up -d tei llm llm-pull
docker compose logs -f llm-pull
```

Дождитесь `success`, затем выйдите из логов через Ctrl+C. В логах TEI дождитесь
готовности модели BAAI/bge-m3 (`docker compose logs -f tei`).

Если на Mac/CPU TEI долго остаётся на `Warming up model` и занимает почти всю
память Docker, для коротких примеров можно использовать отдельную конфигурацию:

```bash
docker compose -p ai-support-desk -f infra/tei/compose.yml -f evals/tei.rag.yml up -d tei
```

Она пересоздаёт только TEI с той же BGE-M3 и тем же томом модели, но ограничивает
батч 1024 токенами и двумя запросами. Это настройка проверки с короткими текстами,
не настройка для произвольных длинных статей: при включённом auto-truncate
TEI может обрезать более длинный вход. Параметры батча описаны в
[документации TEI](https://huggingface.co/docs/text-embeddings-inference/cli_arguments).
Возврат к исходному запуску: `docker compose up -d tei`.

Создайте **отдельную тестовую БД**:

```bash
docker compose -f evals/compose.rag.yml up -d --wait
```

Она использует порт **5436**, пользователя/БД `rag_eval` и тестовый пароль
`rag_eval`. Миграции применяются автоматически при создании этой БД. Она не
использует том основной БД на порту 5433 и не содержит настоящих обращений.
Эти известные тестовые реквизиты предназначены только для локальной проверки.

Запустите загрузку Markdown и три вопроса:

```bash
uv run python -m evals.check_rag --demo --index-demo --output /tmp/rag-results.json
```

При `--demo` DATABASE_URL из `.env` не используется. Флаг `--index-demo`
разрешён только с `--demo`: загрузка примеров не должна запускать очистку
документов в рабочей БД. Примеры в `evals/data/rag_kb` — вымышленные тестовые
правила магазина, не рабочая база знаний.

Скрипт использует существующий `kb-index`: читает четыре Markdown-файла,
получает эмбеддинги BGE-M3 и сохраняет их. Затем на каждый вопрос делает новый
запрос к TEI, выполняет SQL-поиск и передаёт найденные тексты генератору.
При повторном запуске индексатор пропускает неизменённые статьи.

Проверяются:

1. Возврат денег — ответ из одной статьи, срок и способ возврата.
2. Доставка в Казань — стоимость и срок из двух разных статей.
3. Криптовалюта — информации для ответа нет, ожидается эскалация.

В демо выбираются **два** ближайших чанка из четырёх (`--top-k` переопределяет
это значение). Поиск выполняется по косинусному расстоянию, меньше — ближе.
В консоли видны найденные файлы, расстояния, результат и время этапов.
JSON сохраняется после каждого случая, `complete: true` означает завершённый
прогон. Код выхода 1 означает ошибку сервиса или несовпадение с эталоном;
отчёт при этом сохраняется. Тексты вопросов, ответов и найденных документов
входят в отчёт; DSN и пароль туда не записываются.

Отдельный вопрос без повторной индексации:

```bash
uv run python -m evals.check_rag --demo --question 'Когда вернут деньги за отменённый заказ?'
```

Произвольный вопрос не имеет эталона: код выхода 0 подтверждает выполнение
цепочки, а не правильность ответа.

Остановка только тестовой БД:

```bash
docker compose -f evals/compose.rag.yml down
```

В этой конфигурации постоянного тома нет: после `down` демо потребуется
индексировать заново. Основные контейнеры TEI/Ollama останутся запущенными.

## Использование из Worker

```python
from ai_clients.config import AISettings, RagSettings
from ai_clients.rag import open_rag

async with open_rag(AISettings(), RagSettings()) as rag:
    result = await rag.answer_question("Когда вернут деньги?")
    # Вызывающий сервис сохраняет result и организует доставку/эскалацию.
```

Контекст `open_rag` создаётся один раз на время жизни Worker, а не на каждый
вопрос. Он закрывает свои HTTP-клиенты и пул БД. Для тестов или существующего
пула можно создать `RagAnswerer(embedder, search, generator)` с переданными
зависимостями; тогда их жизненным циклом управляет вызывающий код.

Настройки читаются из `.env`:

```dotenv
# Та же БД, в которую выполнена индексация kb-index
DATABASE_URL=postgresql://USER:PASSWORD@127.0.0.1:5433/supportdesk
EMBEDDING_DIMENSION=1024
RAG_TOP_K=5
RAG_SEARCH_TIMEOUT_S=10
# RAG_MAX_DISTANCE не задаётся до калибровки на размеченных примерах
```

TEI должен использовать ту же модель, что использовалась при индексации.
Компонент проверяет размерность вопроса, но совпадение размерности само по
себе не доказывает совпадения моделей. При замене модели нужна переиндексация.

`result` содержит:

- `answer`, `source_ids`, `needs_escalation` — результат существующего генератора;
- `retrieved_chunks` — найденные тексты, хэши, файлы, заголовки и расстояния;
- `reason=no_documents` — выдача пуста после поиска/настроенного отсечения,
  LLM не вызывалась;
- `reason=insufficient_information` — тексты переданы, но генератор отказался
  отвечать по недостаточным сведениям;
- `timings` — время эмбеддинга, SQL-поиска, генерации и всей цепочки.

Технические ошибки дают `RagError` со `stage` равным `embedding`, `search` или
`generation`. Они не превращаются в сообщение «нет информации». Отмена задачи
пробрасывается вызывающему сервису; собственных повторов компонент не добавляет.

## Релевантность и границы оценки

По умолчанию `RAG_MAX_DISTANCE` не задан: выбираются ближайшие чанки без
автоматического утверждения об их пригодности. При необходимости задайте
порог от 0 до 2; он применяется после ранжирования. Это параметр эксперимента,
не готовая оценка уверенности. Для пустого результата без порога нужна пустая
БД; вопрос без ответа может получить близкие по теме, но недостаточные тексты.
В третьем демо-сценарии недостаточность определяет LLM.

Порог нужно подбирать на отдельном размеченном наборе вопросов с ответами и
без ответов. Здесь нет обученного реранкера или универсальной проверки
достоверности. Eval проверяет найденные/указанные источники, эскалацию и
обязательные фразы; правильность каждой формулировки ещё требует оценки.

В схеме нет ANN-индекса. Запрос выполняет точный поиск через pgvector; при
добавлении приближённого индекса в будущем режим поиска нужно пересмотреть.
Замеры этого демо не доказывают производительность на большой базе или при
одновременной обработке обращений. Контекстный бюджет и разделение слишком
длинных статей остаются отдельной доработкой.

## Автотесты

Без Docker:

```bash
uv run pytest libs/ai-clients/tests evals/tests -q
```

Настоящий SQL/pgvector на выделенной БД, без ожидания LLM:

```bash
RAG_TEST_DATABASE_URL=postgresql://rag_eval:rag_eval@127.0.0.1:5436/rag_eval \
uv run pytest libs/ai-clients/tests/test_retrieval_postgres.py -m integration -q
```

Проверяются порядок и числовые расстояния, top-k, отсечение, пустая база и
несовместимая размерность. Изменения тестовых данных откатываются транзакцией.
Отдельные unit-тесты проверяют всю последовательность вызовов, отсутствие
вызова LLM при пустой выдаче, ошибки каждого этапа и расчёт критериев eval.

Результаты выполненной проверки: [06-rag-results.md](experiments/06-rag-results.md).
